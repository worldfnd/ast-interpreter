# ast-interpreter

A small Rust interpreter for Noir's monomorphized AST (`noirc_frontend::monomorphization::ast`).

It can run the same AST over bn254 or Goldilocks and compare field-independent values such as integers,
booleans, arrays, tuples, and structs. `Field` values are deliberately never compared: a difference
there is expected rather than a divergence. The default build uses Noir only.

## Using it

```toml
[dependencies]
ast-interpreter = { git = "https://github.com/worldfnd/ast-interpreter.git", rev = "<rev>" }
```

Use `interpret` for self-checking programs with no inputs, or `interpret_with_inputs` when `main` takes
arguments. For `Prover.toml` inputs, use `inputs_from_prover_toml` and
`expected_return_from_prover_toml`.

Crates that pass Noir AST values into this interpreter must use the same pinned `noirc_frontend` and
`acvm` sources, spelled the same way. Cargo keys a git dependency on the URL *and* the reference, so
`branch = "x"` and `rev = "<head of x>"` are different sources: you get two `FieldElement` types and no
error until the two halves meet. `acvm::FieldElement` is selected at compile time.

The `mavros-oracle` feature is a placeholder. Its `mavros-compiler` dependency is commented out, so
enabling the feature fails the build with a `compile_error!` saying so.

Main exports: `interpret`, `interpret_with_inputs`, `inputs_from_prover_toml`,
`expected_return_from_prover_toml`, `Value`, `IntValue`, `DiffValue`, `DiffOutcome`,
`ComparableError`, `FailureKind`, `RunRecord`, `StepOutcome`, `values_equivalent`,
`outcomes_equivalent`, `outcome_is_tolerated`, `projection_hash`, `canonical_text`, and
`InterpretError`.

`InterpretError` separates bad caller data (`InvalidInput`), runtime range errors
(`ValueOutOfRange`), invalid AST value shapes (`Type`), and interpreter invariant failures
(`Internal`). It and `FailureKind` are `#[non_exhaustive]`.

## Building and testing

Rust 1.89.0, pinned by `rust-toolchain.toml` to the toolchain the pinned Noir crates declare, so a
ledger regenerated here and one regenerated by CI record the same toolchain. `.cargo/config.toml`
raises `RUST_MIN_STACK` because Noir's frontend recurses past libtest's default; it applies only
when cargo runs from this directory. `just --list` shows the recipes CI runs.

```sh
cargo build
```

```sh
just test            # cargo test, then cargo test --features goldilocks
```

## The ledgers

`ledger/bn254.md`, `ledger/goldilocks.md` and `ledger/cross-field.md` are committed photographs
of what the referee observes at the pinned compiler revision: one row per program of Noir's
`test_programs/execution_success` corpus and per fixture under `fixtures/`, with the program's
source hash, the outcome of each step (load, compile, interpret, the check against the `return`
recorded in `Prover.toml`), the returned value, and the hash of a canonical projection of the
monomorphized program (`src/projection.rs`). The cross-field ledger classifies every program's
pair of outcomes: not run (a workspace manifest), equal, equal up to `Field` values, a gap
predicted by a capability tag, a divergence the allowlist records as field-dependent by design, a
stdlib dependency gap, coverage debt (neither side returned a value), an unexpected one-sided gap,
or a divergence.

The ledgers are the cross-revision comparison. CI regenerates all three on every pull request and
push to `main` and fails when a fresh run differs from the committed copy, so an intended change
lands as a reviewed row change described in the pull request, and anything else is a regression.
Divergences are rows, not assertions: the cross-field comparison fails only on harness invariants
(a program missing on one side, a stale allowlist entry, an allowlist entry covering a crash, a
field-independent fixture whose projections differ). Full JSON dumps with triage detail are CI
artifacts (`target/ledger/<field>.json`), never committed.

```sh
just ledger          # sweep bn254, sweep goldilocks, compare; about 7 minutes per sweep
just ledger-check    # the same, then git diff --exit-code -- ledger/
```

The corpus comes from the sibling `../noir` checkout (or `$NOIR_CHECKOUT`), which must be checked
out at the revision the pinned compiler stamped itself with (`noirc_driver::GIT_COMMIT`), with a
clean `test_programs/execution_success`; the sweep refuses anything else. When the sibling is on
another branch, point `NOIR_CHECKOUT` at a worktree of the pinned revision. A test in the default
suite checks that the eleven `worldfnd/noir` pins in `Cargo.toml` agree with each other and with
that stamp, so no path override or stale build can produce a ledger.

Working rule: a pull request moves the compiler pin or the referee's own code, never both, unless
a compiler API change forces it. A pin bump is a reviewed event whose ledger diff is predicted in
its description; the previous rows come from the previous commit, which still pins the previous
compiler.

Some corpus programs are field-dependent by design (`to_*_bytes`/`to_*_bits` sized past the
Goldilocks modulus); `KNOWN_FIELD_DEPENDENT` in `src/ledger.rs` records them and requires each
entry to keep diverging so a stale exclusion surfaces. Programs whose gap a field property
explains (an `i64` input that no Goldilocks element encodes injectively, a `u64` or `Field` input
recorded above the Goldilocks modulus) carry a capability tag in `PROGRAM_CAPABILITIES` instead. Intrinsics the interpreter does not model, such as
`field_less_than` and `array_refcount`/`vector_refcount`, stay `Unsupported` rather than faking a
value for them.

The remaining ignored test, `tests::oracle_survey_execution_success`, runs the corpus through the
interpreter and Noir's own executor and needs a large stack; its doc comment has the command.
